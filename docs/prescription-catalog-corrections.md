# Catalog and drug alias corrections

The actual form preserves extracted labels when options are missing or ambiguous. Reviewers select existing correctly scoped options; they cannot invent IDs or make fuzzy suggestions authoritative. The field helper names the affected catalog. Authorized administrators correct that catalog through Django administration (`/admin/options/`), then the reviewer reloads and explicitly selects the option. Parent/group/protocol relationships remain server-validated. Automatic matches from a changed catalog require fresh selection because their saved fingerprint is stale.

For drug aliases, an administrator with `prescriptions.add_prescriptiondrugalias` creates a proposal at `/admin/prescriptions/prescriptiondrugalias/`. New proposals are pending and do not affect automatic matching. An administrator with `prescriptions.change_prescriptiondrugalias` explicitly selects the proposal and runs **Approve selected drug aliases for automatic matching**. The current administrator and approval time are recorded. Editing an alias or its target revokes approval and requires that action again. Ordinary review users cannot approve. Aliases apply only to existing treatment drugs and inside the resolver's allowed parent scope; conflicting/case-duplicate aliases stay suggestions.

Existing alias rows without an approver remain pending. No backfill silently approves them. Catalog/alias changes never modify immutable extracted evidence, resolve patient identity, approve a review or publish. After correcting the catalog, save the reviewed selection and approve only the saved revision through the existing workflow.
